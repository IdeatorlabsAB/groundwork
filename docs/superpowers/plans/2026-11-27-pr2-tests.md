# PR 2: Tests linked to requirements (both repos) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Solution requirements record the code tests and the test-management cases (any tool) that verify them, locally. The web app's Qase-only case links and recorded runs become tool-neutral, so local links import unchanged.

**Architecture:**
- **Local:** port the web app's `CodeTestLink`, the code-test ops and the tools, and add a tool-neutral `TestCaseLink { tool, id, title, project?, url?, linkedAt, linkedBy }`.
- **Web app:** change `TestCaseLink`, `RecordedTestRun`, `CaseOutcome` and the result matching to the same tool-neutral shape. Old rows and frozen snapshots aren't rewritten. A pure read-time normaliser (`src/lib/test-links.ts`) turns the Qase shape (`caseId: number`, `projectCode`, `provider?`) into the new one wherever items, releases or snapshots are read. Tool inputs still accept the old Qase fields, so connected agents keep working.

**Tech Stack:** TypeScript, zod 4, vitest (both repos). Next.js and React in the web app.

**Spec:** `docs/superpowers/specs/2026-11-26-local-traceability-design.md`, section "Tests (PR 2, both repos)".

## Global Constraints

- Two branches and two PRs:
  - `tests` in `IdeatorlabsAB/groundwork` (this repo);
  - `test-cases` in `ganjilive/centropic-prototype` (`../centropic-prototype`).

  Never push to `main`. Merge only when the user asks and CI passes.
- Case identity is tool + project + id, ignoring case: `caseKey(t) = [t.tool.toLowerCase(), (t.project ?? "").toUpperCase(), t.id.toUpperCase()].join("\u0000")`. The same function lives in both repos and is pinned by the shared fixture `test/fixtures/parity/test-cases.json`, checked in identically in both.
- `tool` is lowercase (`qase`, `testrail`, `xray`, `zephyr`, …). `id` is a string (`"12"`, `"C123"`, `"PROJ-T45"`).
- A legacy web app case `{ provider?, caseId, title, projectCode? }` reads as `{ tool: "qase", id: String(caseId), title, project: projectCode }`. A legacy run `{ provider: "qase", projectCode, id: number, results: [{ caseId, … }] }` reads as `{ tool: "qase", project: projectCode, id: String(id), results: [{ id: String(caseId), … }] }`.
- Code test identity is path + name, exactly as the web app has it (`sameCodeTest`). `path` is repo-relative, with no `..` and no leading `/` (the web app's `codeTest` refine).
- Only solution requirements take tests. Obsolete ones don't. Error wording follows the web app's `testableReq`.
- **Local freezing works like tickets.** A link made before its requirement shipped (`linkedAt <= releasedAt`) can't be unlinked. New links can always be added, including to baseline requirements.
- Result statuses stay the web app's six: `passed | failed | blocked | skipped | invalid | in_progress`. The agent maps a tool's own status to them, e.g. TestRail retest → `failed` and untested → `in_progress`. The tool descriptions say so.
- Ported code carries a header naming its source file, as in PR 1.

## Review Focus

1. **A frozen web app snapshot from before this change** (`tests.projectCode: "ACME"`, `cases: [{ caseId: 12, projectCode: undefined }]`) must still render its report with the case as `ACME-12`. Test: Task 4, `snapshotTests reads a legacy Qase snapshot`.
2. **The same case number in two tools** (Qase `12` and TestRail `12`) linked to one requirement are two cases, and a result for one doesn't count for the other. Tests: Task 1, `linkTestCases keeps cases from two tools with the same id apart`; Task 5, `a TestRail result doesn't pass a Qase case with the same id`.
3. **An agent still sending `{ caseId: 12, projectCode: "acme" }`** to the web app's `link_test_cases` or `record_test_results` must keep working, stored as `qase`/`ACME`/`"12"`. Test: Task 6, `link_test_cases accepts the legacy Qase input`.
4. **Re-linking a case with a new title** refreshes the title and keeps the original `linkedAt`, so a frozen link stays frozen. Test: Task 1, `linkTestCases refreshes the title and keeps linkedAt`.
5. **Importing a local folder with tool-neutral cases into the web app** must keep every case. Today's import schema requires a numeric `caseId` and would reject them. Test: Task 6, `import keeps tool-neutral test cases`.

**Interfaces:**
- Produces:
  - `interface CodeTestLink { path: string; name: string; linkedAt: string; linkedBy: string }`
  - `interface TestCaseLink { tool: string; id: string; title: string; project?: string; url?: string; linkedAt: string; linkedBy: string }`
  - `caseKey(t: Pick<TestCaseLink, "tool" | "id" | "project">): string`, `sameCase(a, b): boolean`, `sameCodeTest(a, b): boolean`, `takesTests(r: Requirement): boolean`. The last is `kindOf(r) === "solution" && r.status !== "obsolete"`.
  - `linkCodeTests(s, c, requirementId, tests: {path,name}[]): Change<number>` and `unlinkCodeTests(...): Change<number>`, ported as they are from the web app's `ops.ts:727-758`.
  - `linkTestCases(s, c, requirementId, cases: Omit<TestCaseLink,"linkedAt"|"linkedBy">[]): Change<number>`. It upserts by `caseKey`. An existing case keeps `linkedAt` and `linkedBy` and takes the new `title` and `url`. Activity text: `linked a test case to "<title>"` or `linked N test cases …`. It returns the number of new cases.
  - `unlinkTestCases(s, c, requirementId, cases: Pick<TestCaseLink,"tool"|"id"|"project">[]): Change<number>`. When it removes the last one, it sets `testCases: undefined`.
