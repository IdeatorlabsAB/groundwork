# PR 3: CI results and test-tool runs, committed — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Test results live in the repository. CI turns JUnit reports into small committed result files on a `groundwork-results` branch. The agent records test-management runs against a product version. Groundwork judges each requirement's tests the way the web app does.

**Architecture:**
- **Port.** The web app's pure JUnit reader (`src/lib/ci/junit.ts`), matching (`match-tests.ts`), latest-result logic (`code-runs.ts`) and test status (`src/lib/tests.ts`) move into `src/core`.
- **Store.** A new `src/store/results.ts` reads and writes the result files.
  - **Readers** take the union of two sources. One is the files on the results branch, read with `git ls-tree`/`git show` from the local branch and from `origin/<branch>`. The other is the working tree's `groundwork/results/`. They're de-duplicated by path.
  - **Writers** put files in the working tree. With `--push`, the file is committed to the results branch through git plumbing (a temporary index), so the checked-out branch and working tree are never touched.
- **Interfaces.** The CLI gets `groundwork results add`, MCP gets `record_test_results`, and `get_item` on a solution requirement shows its test status.

**Tech Stack:** TypeScript, zod 4, `fast-xml-parser` (new dependency, `5.12.1`, as in the web app), git CLI, vitest.

**Spec:** `docs/superpowers/specs/2026-11-26-local-traceability-design.md`, section "CI results (PR 3)".

## Global Constraints

- Branch `results` in `IdeatorlabsAB/groundwork`, one PR. Never push to `main`. Merge only when the user asks and CI passes. No web app changes in this PR.
- **Shapes match the web app's** so PR 7 imports them unchanged:
  - Code run: `{ id, commitSha, ref, at, source: "ci", results: CodeTestResult[] }`, where `CodeTestResult = { path, name, status: "passed"|"failed"|"skipped", durationMs? }`.
  - Test-tool run: `{ source: "test-tool", tool, project, id, title, url?, product, version, results: [{ id, status, endTime: string|null }], recordedAt, recordedBy, via? }`. Statuses are the web app's six.
- **File paths** *(builder's call, revised after the plan review)*:
  - code runs: `groundwork/results/ci/<YYYYMMDDTHHMMSSZ>-<sha7>-<job>.json`. `<job>` is `<GITHUB_RUN_ID>-<GITHUB_RUN_ATTEMPT>-<GITHUB_JOB slug>` in GitHub Actions, otherwise 8 random hex characters. Names sort by time and never collide.
  - test-tool runs: `groundwork/results/tools/<tool>-<slug(project)>-<slug(runId)>-<hash8>.json`, where `hash8` is the first 8 hex characters of sha1(`tool\0PROJECT\0runId`). Recording the same run again overwrites it, and `Run #1` and `run-1` don't collide.
  - Every repository path is built with `path.posix`.
- **Where each kind lives.**
  - **CI runs** are committed to the results branch by `results add --push`, and only there: `--push` doesn't also write the working tree. They're read from `origin/<resultsBranch>` (and from the working tree, for a CI job that writes without pushing). On a path clash, the branch wins.
  - **Test-tool runs** are written to the working tree by `record_test_results` and committed with ordinary commits and PRs. They're read from the working tree only.
- **Monorepos.** `groundwork/` may sit in a subfolder of the repository. Every git path is the repository prefix (`git rev-parse --show-prefix`) plus `groundwork/results/...`. Reads use `ls-tree --full-name` and strip the prefix.
- **Code runs count only on the default branch, from CI.**
  - Each run stores `ref`, `defaultBranch: boolean` (decided when it's written: the GitHub event file's `repository.default_branch` when `$GITHUB_EVENT_PATH` exists, else `config.yml`'s `defaultBranch`), `source: "ci"` (only when `$CI` is set), else `"local"`, and `totals: { passed, failed, skipped }` over the whole report.
  - `id` is a random UUID.
  - Only `source: "ci"` runs with `defaultBranch: true` count. The newest `CODE_RUN_WINDOW = 30` by file name are read, and older files aren't parsed.
- New optional `config.yml` keys: `defaultBranch` (default `main`) and `resultsBranch` (default `groundwork-results`). No `schemaVersion` bump.
- **What a code run keeps.** Every result in the test files that some linked code test points to, not just the linked tests. That keeps the web app's rule that a file's newest run is its current set of tests, so a deleted test stops counting. Files are pretty-printed JSON with a trailing newline. There's no `--all`.
- **For PR 7:** the import will send the 30-run window plus the runs that sign-off snapshots cite, not every file, to stay under the 4 MB cap.
- `groundwork import` refuses a folder that has results, as it does for risks, until PR 7 carries them.
- Ported files carry a header naming their web app source.

## Review Focus

0. **A repository where `groundwork/` is in a subfolder.** `--push` writes to `<prefix>groundwork/results/...`, and readers find it there. Test: Task 3, `--push and the readers agree when groundwork/ is in a subfolder`.
1. **CI with a shallow checkout** (`actions/checkout` fetches only the PR or main branch, so `groundwork-results` and `origin/groundwork-results` aren't present locally). `results add --push` must fetch it with an explicit refspec (`+refs/heads/<b>:refs/remotes/origin/<b>`, `--depth=1`), checking first with `git ls-remote --exit-code`, and create it when the remote doesn't have it. Tests run in a `git clone --depth 1 --single-branch` clone. Task 3: `--push creates the results branch on a remote that doesn't have it` and `--push adds to an existing results branch from a single-branch shallow clone`.
2. **Several CI jobs pushing at the same time.** A rejected push (non-fast-forward or fetch first) is refetched and re-applied, up to 5 attempts with a random 0.2–1 s wait. Any other push error (auth, 403, missing `contents: write`) fails at once with a hint. A push that finally fails exits 1: missing evidence should be visible. Tests: Task 3, `--push retries on top of a concurrent push` and `--push doesn't retry an auth failure`.
2b. **A CI runner with no git identity.** `commit-tree` gets `GIT_AUTHOR_*` and `GIT_COMMITTER_*` in its environment. Test: Task 3, `--push works without a git identity` (with `HOME` set to an empty folder).
3. **A JUnit report with tests no requirement links.** Only results from files a linked test points to are kept. A run with nothing linked still writes a file with empty `results` and full `totals`. Test: Task 3, `keeps the results of linked files, and writes a run with none`. Also Task 2, `a linked test deleted from a kept file stops counting`.
4. **The working tree holds a result file the branch also has**, e.g. after a local `results add` followed by a push. It's counted once. Test: Task 2, `a file in both places counts once`.
5. **A malformed result file** (bad JSON, missing `results`) is skipped with a warning that `validate` reports. It doesn't crash readers. Test: Task 2, `a malformed result file is skipped and reported`.

### Task 3: `groundwork results add`, with `--push`

**Files:**
- Create: `src/store/results-cli.ts`, exporting `runResultsCommand(root, cwd, opts)`, which returns `Promise<{ code: number; lines: string[] }>`
- Modify: `src/store/results.ts`, adding `pushResult(root, rel, json, opts: { branch: string; message: string; attempts?: number; beforePush?: () => void }): { attempts: number }`
- Modify: `src/cli.ts` (the `results` command; flags `commit`, `ref`, `push`, and a hidden `at`; HELP)
- Test: `test/results-cli.test.ts`

**Behaviour:** `groundwork results add <junit file or glob>… [--commit <sha>] [--ref <ref>] [--push]`
- **Inputs.** Globs resolve from the current directory (`fs.globSync`). `--commit` falls back to `$GITHUB_SHA`, then `git rev-parse HEAD`. `--ref` falls back to `$GITHUB_REF`, then `git symbolic-ref -q HEAD`. `source` is `"ci"` when `$CI` is set, otherwise `"local"`, and a local run prints `Not in CI: this run won't count as evidence.`.
- **What it writes.** Each report goes through `parseJunit` and then `keepLinked`.
  - Without `--push`, the file goes to the working tree.
  - With `--push`:
    1. `ls-remote --exit-code origin refs/heads/<b>`. Exit 2 means the branch is missing.
    2. If it exists, `fetch --depth=1 origin +refs/heads/<b>:refs/remotes/origin/<b>`.
    3. A temporary index (absolute path) with `read-tree` of origin/<b> (or empty), then `update-index --add --cacheinfo 100644,<blob>,<prefix+rel>`, then `write-tree`.
    4. `commit-tree` with the parent when it exists, and `GIT_AUTHOR_NAME`/`GIT_COMMITTER_NAME` set to `groundwork` and `_EMAIL` set to `groundwork@localhost` unless the environment already sets them.
    5. `push origin <commit>:refs/heads/<b>`. A rejection retries from step 1, up to 5 attempts with jitter. Any other error stops at once.
- **Messages.** `Wrote <rel>: <n> results from <f> linked test files (<total> in the reports).` and `Pushed to <branch>.`. These are errors with exit 1:
  - `No JUnit files match <patterns>.`;
  - a `JunitError` naming its file;
  - `Couldn't push results to <branch>: <git's message>. In GitHub Actions the job needs permissions: contents: write.`
