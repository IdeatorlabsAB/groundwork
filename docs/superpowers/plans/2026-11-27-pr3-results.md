# PR 3: CI results and test-tool runs, committed — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Test results live in the repository. CI turns JUnit reports into small committed result files on a `groundwork-results` branch. The agent records test-management runs against a product version. Groundwork judges each requirement's tests the way the web app does.

**Architecture:**
- **Port.** The web app's pure JUnit reader (`src/lib/ci/junit.ts`), matching (`match-tests.ts`), latest-result logic (`code-runs.ts`) and test status (`src/lib/tests.ts`) move into `src/core`.
- **Store.** A new `src/store/results.ts` reads and writes the result files.
  - **Readers** take the union of two sources. One is the files on the results branch, read with `git ls-tree`/`git show` from the local branch and from `origin/<branch>`. The other is the working tree's `groundwork/results/`. They're de-duplicated by path.
  - **Writers** put files in the working tree. With `--push`, the file is committed to the results branch through git plumbing (a temporary index), so the checked-out branch and working tree are never touched.
- **Interfaces.** The CLI gets `groundwork results add`, MCP gets `record_test_results`, and `get_item` on a solution requirement shows its test status.

**Tech Stack:** TypeScript, zod 4, `fast-xml-parser` (new dependency, `5.12.1`, as in the web app), git CLI, vitest.

**Spec:** `docs/superpowers/specs/2026-11-26-local-traceability-design.md`, section "CI results (PR 3)".

## Global Constraints

- Branch `results` in `IdeatorlabsAB/groundwork`, one PR. Never push to `main`. Merge only when the user asks and CI passes. No web app changes in this PR.
- **Shapes match the web app's** so PR 7 imports them unchanged:
  - Code run: `{ id, commitSha, ref, at, source: "ci", results: CodeTestResult[] }`, where `CodeTestResult = { path, name, status: "passed"|"failed"|"skipped", durationMs? }`.
  - Test-tool run: `{ source: "test-tool", tool, project, id, title, url?, product, version, results: [{ id, status, endTime: string|null }], recordedAt, recordedBy, via? }`. Statuses are the web app's six.
- **File paths** *(builder's call, recorded here)*:
  - code runs: `groundwork/results/ci/<YYYYMMDDTHHMMSSZ>-<sha7>.json`, which sorts by time;
  - test-tool runs: `groundwork/results/tools/<tool>-<project or "_">-<runId slug>.json`, so recording the same run again overwrites it.
- **Code runs count only on the default branch.** `ref` is normalised (`refs/heads/main` → `main`) and must equal `defaultBranch`. The newest 30 such runs are read (`CODE_RUN_WINDOW = 30`).
- New optional `config.yml` keys: `defaultBranch` (default `main`) and `resultsBranch` (default `groundwork-results`). No `schemaVersion` bump.
- A code run keeps only results for tests linked to some requirement, unless `--all` is given. Files are pretty-printed JSON with a trailing newline.
- `groundwork import` refuses a folder that has results, as it does for risks, until PR 7 carries them.
- Ported files carry a header naming their web app source.

## Review Focus

1. **CI with a shallow checkout** (`actions/checkout` fetches only the PR or main branch, so `groundwork-results` and `origin/groundwork-results` aren't present locally). `results add --push` must fetch the branch first, and create it when the remote doesn't have it. Test: Task 3, `--push creates the results branch on a remote that doesn't have it`.
2. **Two CI jobs pushing at the same time.** The second push is rejected as non-fast-forward. It must refetch, re-apply its file on top, and retry once rather than fail the job. Test: Task 3, `--push retries once on top of a concurrent push`.
3. **A JUnit file with tests no requirement links.** Only linked tests are kept, and a run with nothing linked still writes a file (with an empty `results`), so "the latest CI run" stays correct. Test: Task 3, `keeps only linked tests, and writes a run with none`.
4. **The working tree holds a result file the branch also has**, e.g. after a local `results add` followed by a push. It's counted once. Test: Task 2, `a file in both places counts once`.
5. **A malformed result file** (bad JSON, missing `results`) is skipped with a warning that `validate` reports. It doesn't crash readers. Test: Task 2, `a malformed result file is skipped and reported`.

### Task 3: `groundwork results add`, with `--push`

**Files:**
- Create: `src/store/results-cli.ts`, exporting `runResultsCommand(root, opts): Promise<{ code: number; lines: string[] }>` (the `runReleaseCommand` style)
- Modify: `src/cli.ts` (the `results` command, new flags `commit`, `ref`, `all`, `push`, `at`; HELP text)
- Modify: `src/store/results.ts`, adding `pushResult(root, rel, json, resultsBranch, message): { pushed: boolean; retried: boolean }`
- Test: `test/results-cli.test.ts`, using a bare repo as `origin` and a clone as the CI checkout

**Interfaces:**
- `groundwork results add <junit file or glob>… [--commit <sha>] [--ref <ref>] [--at <iso>] [--all] [--push]`:
  - **Defaults.** `--commit` falls back to `$GITHUB_SHA`, then `git rev-parse HEAD`. `--ref` falls back to `$GITHUB_REF`, then `git symbolic-ref -q HEAD`. `--at` defaults to now. Globs are expanded with Node's `fs.globSync` (Node 22).
  - **Output.** It prints `Wrote <path>: <n> results for linked tests (<m> in the reports).`. With nothing linked it prints `… 0 results for linked tests …` and still writes the file.
  - **Exit codes.** 1 when no file matches, with the message `No JUnit files match <patterns>.`. 1 on a `JunitError`, with the file named.
  - **`--push`** commits only that file to `resultsBranch` through plumbing:
    1. `git fetch origin <branch>` (a missing branch is fine);
    2. `GIT_INDEX_FILE=<tmp>`, then `git read-tree <origin/branch or empty>`;
    3. `git update-index --add --cacheinfo 100644,<blob>,<rel>`;
    4. `write-tree`, then `commit-tree` (parent = origin/branch if it exists; message `Groundwork results: <rel>`);
    5. `git push origin <commit>:refs/heads/<branch>`.

    On a rejected push it repeats once from step 1, then exits 1 with `Couldn't push results to <branch>: <git's message>`. The commit uses `GIT_AUTHOR_NAME`/`EMAIL` if set, else `groundwork <groundwork@localhost>`. The working tree file is still written.

**Interfaces:**
- **`record_test_results { product?, version, run: { tool, project, id, title, url? }, results: { id, status, endTime? }[] (≤ 2000) }`**. Its description is the web app's tool-neutral one, with "release" read as "product version". It:
  - resolves the product with `s.targetProduct`;
  - requires `version` to be a version of it. An unknown version gives `"<v>" isn't a version of <title>. Versions: …`. A released version gives `<title> <v> is released, so its test results can't change.`;
  - needs `endTime` for finished results, with the web app's message (tool wording);
  - writes `testRunPath(run)` in the working tree. Recording the same run again overwrites it.
  - returns `{ recorded: { file, results: n }, tests: { <requirement id>: RequirementTestStatus } }` for the solution requirements planned for that version that have tests linked.
- **`get_item` on a solution requirement** adds `tests: RequirementTestStatus` when it has tests linked. The status is judged for `releasedIn ?? plannedFor` of its product, with `resultsFor`. Without a version, only code runs count.
- **`buildBundle`** refuses when `loadResults` finds any run: `This folder has test results, and the web app's import doesn't carry them yet. …`. The import tests remove `groundwork/results`.
