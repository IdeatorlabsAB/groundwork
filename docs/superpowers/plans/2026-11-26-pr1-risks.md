# PR 1: Risks with mitigations — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local `RSK` risk kind scored on a configurable matrix, with mitigating requirements linked on both sides, risks in the baseline, `trace_code`, and the risk skill — shaped like the web app's `Risk` so PR 7 can import it unchanged.

**Architecture:** Port the web app's pure `src/lib/risk.ts` and `src/lib/code-refs.ts` into `src/core`. Add `risks` as a new collection that rides the existing generic file store (`load`/`save`/`assignIds`/`renumber`). Expose it through the web app's MCP tool names (`add_risks`, `update_item`, `link_items` risk → requirement, `delete_item`, `search_items`, `get_item`, `get_workspace.riskMatrix`, `trace_code`) so an agent's workflow is the same on both servers.

**Tech Stack:** TypeScript, zod 4, `yaml`, `@modelcontextprotocol/sdk`, vitest.

**Spec:** `docs/superpowers/specs/2026-11-26-local-traceability-design.md` (section "Risks (PR 1)").

**Plans for PRs 2–7** are written one at a time, each when its turn comes, because each builds on the previous PR's interfaces.

## Global Constraints

- Work on branch `risks` in `IdeatorlabsAB/groundwork`. Open a PR; never push to `main`. Merge only when the user asks and CI passes.
- The design doc and this plan are committed on this branch, in the first commit.
- Ids are `RSK-` plus at least four digits, never reused. Files are `groundwork/risks/<id>-<slug>.md`.
- Field names match the web app's `Risk` (`centropic-prototype/src/lib/types.ts:294`), except `versions` (the local form of `releaseIds`, holding version strings of the risk's product) and the additions `category`, `domain`, `origin`, `originNote`.
- Levels are never stored. They are always derived from the matrix.
- Default matrix: `defaultMatrix(5)`, exactly as in the web app's `risk.ts`. Allowed sizes are 3 and 5.
- No `schemaVersion` bump: the new kind and fields are optional.
- Ported files start with a comment naming their web app source, e.g. `// Ported from centropic-prototype src/lib/risk.ts. Keep in step with it (see test/fixtures/parity).`
- Tool names and error wording follow the web app (`centropic-prototype/src/lib/server/mcp/server.ts`) wherever it has the same tool.
- Every new rule lives in `src/core` or `src/store`, not in the MCP handler, unless it needs `Session`.

## Review Focus

1. **A risk tagged for the baseline version, then a mitigation added in 1.1.** Linking a mitigation to an already released requirement must work, because that's how existing controls are recorded. `riskIds` on a requirement is not part of its release record. Test: Task 4, `link_items risk -> released requirement succeeds`.
2. **The matrix changes from 5 to 3 after risks exist.** Scores above 3 become unplaceable. `validate` must report each one as an error naming the risk and the field, not crash. `get_item` shows `level: "unscored"`. Test: Task 3, `validate reports scores outside a shrunk matrix`.
3. **A hand-edited `config.yml` with a malformed `riskMatrix`** (wrong row count, unknown level) must give a clear `ConfigError`, not silently fall back to the default. Test: Task 1, `readConfig rejects a malformed riskMatrix`.
4. **Renumbering on a branch** must rewrite `mitigationIds` and `riskIds` like other links, or a clash fix breaks the risk register. Test: Task 3, `renumber rewrites mitigationIds and riskIds`.
5. **Deleting a requirement that mitigates a risk** must remove it from `mitigationIds`, so validate doesn't report a dangling link. Deleting a risk must also clear `riskIds`. Test: Task 2, `deleteRequirement drops it from risks' mitigationIds`.

### Task 4: MCP tools for risks, and trace_code

**Files:**
- Create: `src/core/code-refs.ts` (port of the web app's `code-refs.ts`: `refPath`, `touches`)

**Interfaces:**
- Consumes: Tasks 1–3.
- Produces:
  - `Session.matrix: RiskMatrix`.
  - `Session.checkScores(p)`, with the web app's message: `probability must be a whole number from 1 to 5 on this workspace's 5×5 risk matrix (got 6).`
  - `Session.checkRiskVersions(product: Product, versions: string[], was: string[] = [])`. Every version must belong to the product. Any version added or removed (compared with `was`) must be planned. The error is `"1.0" is released, so a risk can't be added to it or removed from it.`
  - `Session.levels(r)`, which returns `{ level: RiskLevel | "unscored", residualLevel? }`.

  Tool behaviour:
  - **`get_workspace`**: adds `riskMatrix: s.matrix`. `counts.risk` comes for free from `KIND`.
  - **`add_risks`** `{ risks: riskInput[] (1–30) }`, with the web app's description, using "versions" for "releaseIds".
    - Resolves `product` with `s.targetProduct(r.product)` (the only product when there's one) and stores the product id.
    - Checks scores and versions, and resolves `productArea`.
    - Sets `owner` to the actor and `mitigationIds: []`.
    - Returns `{ created: summary[] }`, where each summary includes `level`.
  - **`update_item`** on a risk:
    - parses with `PATCHES.risk`;
    - checks scores;
    - calls `checkRiskVersions` with the old versions when `versions` is in the patch;
    - refuses to change `product` once `versions` is non-empty: `"<title>" is tagged for versions of <product>, so its product can't change.`;
    - then runs `ops.updateRisk`.
  - **`link_items`** with a risk `id` and requirement targets: `ops.linkMitigation` for each target, allowed even when the requirement is released. The `releaseRecordReason` lock stays only for requirement → x links. A requirement `id` with a risk target gives the error `Link the other way: link_items from the risk to the requirement.`
  - **`delete_item`** on a risk: `ops.deleteRisk`.
  - **`search_items`**: `kind: "risk"` works, and summaries of risks include `level` and `residualLevel`.
  - **`get_item`** on a risk returns `item` with the levels and `mitigatedBy` (summaries of the mitigation requirements) and `mitigated: isMitigated(...)`. `get_item` on a requirement with `riskIds` lists those risks in `linksTo`.
  - **`trace_code`** `{ paths: string[] (1–200) }`, with the web app's description and output shape `{ paths: [{ path, requirements, risks }] }`. Obsolete requirements are left out.
  - `INSTRUCTIONS` gets the web app's `Risk:` bullet (line 50 there), changed to say versions, plus one line under "When you plan work": `Call trace_code on the files in scope; a hit on a risk or a mitigating requirement means the change affects that risk.`
